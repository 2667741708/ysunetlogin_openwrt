# 校园网 0：UDP 握手与云 WireGuard 追踪

日期：2026-09-15。本文是实机观察记录，不代表已经取得学校或节点运营方的网络策略。

## 结论

故障已缩小到校园网 0 下的 UDP 连接通路，发生在完成 TUIC/WireGuard 握手之前。
普通 Cloud WireGuard 没有修复本次问题：同机移动下完整链路可用，校园网 0 下 WG 自己就无法完成握手。
具体丢弃设备、规则及方向尚未确认，不能据此认定学校封禁了全部 UDP。

## 同机 Cloud WG 对照

每轮核实实际认证服务，使用独立临时内核、新 WG/TUIC 会话和同一个固定节点 IPv4。
云端原 WG 仅用于 peer 互通，没有公网 NAT。本次为唯一临时 peer 添加定向转发，
只允许它访问所测射手座 IP 的 UDP/22892，不接管本机其他网络流量。

校园网 0 日志反复出现 WG 发起握手、5 秒没有完成后重试。失败发生在到达云端后再使用
射手座之前，不能只靠更改射手座密码、网站分流或 TUIC 中继参数解释。
移动下云端可观察到 WG 解密、定向 NAT、射手座回包和返回 WG 的完整双向流量。

## 包记录和路径观察

- D321 停用借网并核实校园网 0 后，两轮有效 IP 层观察各有 20 条 QUIC v1 Initial，
  握手 IP 包长 1308 字节、UDP 有效载荷 1280 字节；未见节点回包或相关 ICMP 错误。
- 观察器先用校园 DNS 请求/响应验证。最初未捕获到验证包的 PktMon 空记录已排除，
  采用原始 IP 接收记录；该观察点不等于交换机镜像口，不能证明每条记录已离开网线。
- UDP TTL 1–16 未得到逐跳回复，不能从这些记录指出具体丢弃路由器。
- 本机 ICMP 路由跟踪显示 0 与移动在校内汇聚点之后走不同路径。
  ICMP 路由不等于同一 UDP 流的完整路径；星号不代表业务流量必然丢失。
- 追加的云端 UDP/51820 抓包中，移动前后均有新握手和回复；校园网 0 的核验窗口内未见新握手。
  为减少无关流量，捕获排除了三个既有 peer 的来源地址，结论受该范围限制。
- 云厂商安全组位于主机抓包点之前，当前没有其控制面权限；不能排除按来源过滤等原因。
- 新增端口回显的移动阳性对照也未成功，故未用这组结果判断校园网端口限制。
  一次追加试验的临时代理入口连接被拒绝，该次网页请求也没有用于独立因果判断。

## 下一步如何确认具体根因

需要学校网关上的校园网 0 服务模板、出口 ACL、UDP/NAT 日志，或云平台安全组丢弃记录，
或射手座端点对应时段的入站抓包。两端记录可以区分正向与回程故障。
没有这些观察点，继续重复 traceroute 不会自动显示隐藏的丢弃规则。

当前适用的办法仍是：校园网 0 使用已测通的 TCP/443 节点，或
“TCP/443 前置 → 射手座”的链式连接。详见 [配置方法](CAMPUS_PROXY_DIAGNOSIS.md)。
WG 外再套 TCP/HTTPS 是另一种方案，本次没有部署或验证，不能标记为已可用。

测试结束已恢复本机移动和 D321 原借网，清理云端临时 peer、转发/NAT/入站规则及观察器。
原 WG 服务、既有 peer 和日常 Clash 配置保留。原始包文件与详细地址记录仅保存于本机证据目录。
