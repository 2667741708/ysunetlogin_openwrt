# 校园网 0 与代理：D321 实机排查

后续实测：[UDP 包路径与 Cloud WireGuard 追踪](CAMPUS_PACKET_TRACE.md)。原生云 WG 在校园网 0 下也未完成握手，具体丢弃规则尚未确认。

日期：2026-09-15。测试位置：教学区有线；系统：Windows。

## 结论

校园网 0 可以使用代理。本次已在停用借网、核实校园网 0 会话的 D321 上，
通过修复后的本地代理访问 GitHub 和百度，均得到 HTTP 200。
某一节点不可达、代理端口不可用、校园认证未成功，是三个需要分别检查的问题。

## 本次发现的三个问题

### 1. 有线认证检查误报失败

校园 DNS 和认证 HTTPS 可达，但 HTTP 认证网关不回应 Python 默认 User-Agent。
同一网卡、相同请求改用浏览器标识后立即得到响应，HTTP/1.0 和 HTTP/1.1 均可复现。
网关返回的是 `top.self.location.href` 页面脚本跳转。

`campus_network.py` 现使用浏览器标识，安全提取校园 HTTPS 跳转，
限制跳转次数并核对会话中的出口 IP。不会执行页面 JavaScript。
修复后，D321 可独立取得认证会话并登录校园网 0。

### 2. D321 残留的强制中转规则

Clash 的第一条规则为：

```text
MATCH,Codex-4090-Relay
```

该中转指向 `127.0.0.1:17897`，实际没有服务监听。日志记录连接被拒绝。
这条规则会匹配所有请求，导致后面的正常分流和节点选择不起作用。
因此会出现“节点检测成功，但浏览器或命令行走代理失败”。

已备份 D321 配置，移除运行配置中的这条强制规则，并修正生成规则的配置脚本，
防止刷新配置后再次注入。保留原节点、正常规则和自动选择设置。
系统代理开关仍保持原状态；测试用请求明确指定本机代理端口。

#### 为什么会留下？每次借网都会生成吗？

D321 原配置脚本的注释明确写着通过本机 SSH 隧道使用 C201 4090 的代理。
它添加一个 HTTP 中转节点，再将 `MATCH,Codex-4090-Relay` 放到规则首位。
SSH 转发停止后，配置没有随之恢复，于是代理继续访问无人监听的本机端口。
该脚本在 Clash 重新生成配置时会再次注入规则；不是每次 WireGuard 借网必然生成。
本次既移除了运行规则，也修正了生成脚本，因此刷新不会按原逻辑加回强制规则。

已检查网络管理面板当前源码：默认借网只处理网络路由；勾选共享代理时，
Windows 辅助程序会备份用户代理并设置为“出口隧道 IP:17897”，完整断开时恢复。
该流程不写 Clash 的配置脚本，也不注入上述 `MATCH`。
这里端口同为 17897，但“出口隧道 IP”与“本机 127.0.0.1”是两个不同入口。
桌面面板的暂停隧道操作与管理台的完整断开清理也有区别。

### 3. TUIC 节点与 TCP/443 节点表现不同

在已核实的校园网 0 会话下，逐个指定节点检测 GitHub：

| 节点 | 传输配置 | 首轮检测 |
| --- | --- | --- |
| 东京-E（通用） | VLESS / WebSocket / 443 | 成功，103 ms |
| 香江-E（通用） | VLESS / WebSocket / 443 | 成功，154 ms |
| 香江-F（通用） | VLESS / WebSocket / 443 | 成功，78 ms |
| 射手座-A（通用） | TUIC / 22892 | 失败 |

移除失效中转规则后，校园网 0 下连续两轮经本机代理访问 GitHub、百度均返回 HTTP 200；
同时香江-F 的两轮节点检测均为 79 ms。部分其他节点曾超时、复测恢复，节点健康情况会变化，
不能把首次成功当作永久保证。

TUIC 使用 QUIC；其连接路径与本次可用的 TCP/443 节点不同。
现有证据只支持“这条 TUIC 链路在该条件下不可用”，不能证明学校封禁了所有 UDP 或所有代理。
协议参考：[Mihomo TUIC](https://wiki.metacubex.one/config/proxies/tuic/)、
[VLESS](https://wiki.metacubex.one/config/proxies/vless/)。

### 4. 本机进一步排除 DNS、IPv6 和常用 TUIC 参数

同日，在本机同一 iYanDa Wi-Fi、同一物理网卡、同一账号上执行
“移动 → 校园网 0（两轮）→ 移动”。每轮前后核验学校返回的实际运营商。
每轮启动独立的临时 Mihomo 进程，避免复用上轮连接；不改变日常 Clash 配置或系统代理。
各节点检测目标均为 GitHub HTTPS，10 秒超时。

| 配置 | 移动（切换前） | 校园网 0 第一轮 | 校园网 0 第二轮 | 移动（恢复后） |
| --- | --- | --- | --- | --- |
| 射手座-A 原配置 | 成功 787 ms | 失败 | 失败 | 成功 1183 ms |
| 同节点固定校园 DNS 解析的 IPv4 | 成功 650 ms | 失败 | 失败 | 成功 1268 ms |
| 固定 IPv4，并改为 quic 中继模式 | 成功 812 ms | 失败 | 失败 | 成功 679 ms |
| 固定 IPv4，改 cubic 与 10 秒握手超时 | 成功 1159 ms | 失败 | 失败 | 成功 980 ms |
| 香江-F，VLESS / WS / TCP 443 | 成功 1902 ms | 成功 600 ms | 成功 606 ms | 成功 2483 ms |

这里“失败”指本机 Mihomo 节点检测 API 返回 503，不是目标网站返回 503。
固定同一 IPv4 后仍然出现严格随运营商变化的结果，说明简单改 DNS、关闭 IPv6、
调整本次所试 TUIC 参数没有修复这条链路。问题集中在校园网 0 出口到该 TUIC 端点的路径。
尚无抓包、学校策略或节点服务端日志，不能进一步断言是哪一端的 UDP/端口过滤、路由或访问策略。

`udp-relay-mode: quic` 不会把 TUIC 的底层连接改成 TCP；只改客户端端口也不能让服务端
自动支持新端口。字段含义见 [TUIC 官方配置说明](https://wiki.metacubex.one/config/proxies/tuic/)。

### 5. 已测通的射手座连接办法：经过 TCP/443 前置节点

在独立临时配置中，让射手座-A 使用香江-F 作为 `dialer-proxy`：

```text
本机（校园网 0） → 香江-F（VLESS / WS / TCP 443） → 射手座-A（TUIC） → 网站
```

第一次链式对照中，校园网 0 首轮前置节点和链式节点都超时；第二轮前置恢复后，
链式节点成功 738 ms，而直接连接射手座仍失败。
随后新增实际网页请求验证：

| 校园网 0 下的检查 | 第一轮 | 第二轮 |
| --- | --- | --- |
| 直接连接射手座-A | 失败 | 失败 |
| 香江-F 前置节点 | 成功 639 ms | 成功 592 ms |
| 经香江-F 连接射手座-A | 成功 773 ms | 成功 715 ms |
| GitHub HTTPS 经完整链路 | HTTP 200，curl 退出 0 | HTTP 200，curl 退出 0 |
| 百度 HTTPS 经完整链路 | HTTP 200，curl 退出 0 | HTTP 200，curl 退出 0 |

每轮重新启动独立内核，测试代理入口仅监听本机，全部请求明确指定该入口，
最终规则指向链式射手座节点，没有回退直连或其他节点。会话前后均核实为校园网 0。
测试中用校园 DNS 解析的同一 IPv4 固定射手座端点，保留订阅原有身份和 TLS 字段。
最后已恢复移动；临时进程和含节点信息的临时配置均已清理，日常 Clash 配置未替换。

#### 配置方法

这是 Clash/Mihomo 的设置，不是 netlogin 的运营商参数。

1. 保留原射手座和香江-F 节点。复制完整的射手座节点条目，保留服务器、端口、身份、TLS 等原字段。
2. 将副本改名为“射手座-A（经香江-F）”，在副本里增加下面两个字段。
   `dialer-proxy` 的值须照抄自己订阅里香江-F 的完整名称，包括表情、空格和括号。

   ```yaml
   # 这是对完整副本的修改片段，不是独立可用的节点定义。
   name: 射手座-A（经香江-F）
   dialer-proxy: "填写订阅中香江-F节点的完整名称"
   ip-version: ipv4
   ```

3. 为完全复现本次固定端点测试，可在副本中再填 `ip: 当前校园 DNS 解析出的真实 IPv4`。
   保留原 `server` 和 TLS/SNI 设置；不要把域名、端口和证书名称随意改掉。
   固定 IP 会随提供商变更而过期，需要更新；本次固定 IP 的目的为排除 DNS 差异。
4. 将副本加入手动节点选择组，重载后选择这个副本。使用 Clash 的持久覆写机制保存，
   避免只修改自动生成文件而在订阅刷新时丢失。不要添加置顶 `MATCH` 强制全局中转。
5. 先确认校园账号实际为 0，再检查前置节点和完整链路，最后测试实际目标网页。

这条方案仍使用射手座作为最后一跳，但会增加一跳、延迟和前置节点流量；两个节点都要可用。
第一次测试的超时说明它不是无条件稳定。网页复测的移动基线中也曾收到 HTTP 200 后下载超时
（curl 退出 28），所以不能只看 HTTP 状态码就宣称请求完整成功。
若不要求射手座作为最后一跳，直接使用可用的 TCP/443 节点更简单；若要直接连接射手座，
当前已验证的方法是使用移动出口。仅修改 netlogin 无法改变节点服务端或校园出口的网络策略。

机制参考：[Mihomo dialer-proxy](https://wiki.metacubex.one/config/proxies/dialer-proxy/)。
并非任意前置节点都能承载 TUIC，本次结论限于实际测试的节点组合。

## 使用方法

1. 先确认校园账号和实际服务：`python netlogin.py current-status`。
2. 独立测试前，在网络管理面板停用借网，并核对认证出口属于测试机。
3. 检查 Clash 规则是否存在置顶的强制 `MATCH`，以及它指向的服务是否在运行。
4. 在校园网 0 下优先测试已测通的 TCP/443 节点，例如本轮的香江-F；不要只看节点名称。
5. 运营商切换后给旧会话释放和代理重连留出时间，再重复访问实际目标网站。

不能只把 TUIC 节点端口改成 443；对端必须支持所选协议和端口。
学校指定的认证入口及触发方式见[实名认证系统通知](https://notice.ysu.edu.cn/info/2073/24740.htm)。

## 验证边界

- 面板停用借网后，WireGuard 服务为 Stopped / Disabled；认证会话 IP 与 D321 物理网卡一致。
- D321 的移动认证未通过核验，本轮没有完整的同机 0/移动对照。
- 本机电脑未发现 D321 的强制中转残留，不能把 D321 的配置故障套用到本机。
  本机此前的同机对照显示，所选 TUIC 节点在校园网 0 失败、恢复移动后可用。
- 测试账号密码未写入脚本或诊断报告。修复不关闭 TLS 证书验证，不变更校园运营商选择规则。
- 最后注销 D321 临时测试会话，经同一网络管理面板恢复原借网启动配置和连接；失效中转规则的修复保留。
