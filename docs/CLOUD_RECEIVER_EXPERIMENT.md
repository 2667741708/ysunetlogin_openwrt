# Cloud 接收端实验：校园网 0 的包是否到达、是否返回

日期：2026-09-15，约 21:18–21:28（北京时间）。本轮测试应用层 UDP 回显。

## 结论

D321 在校园网 0 下，直接向 cloud 发送的 80 和 1280 字节 UDP 数据都完成了完整往返；
经香江-F 也完成了往返。因此，不能认定校园网 0 一概阻断外网 UDP 或 UDP 回包。

D321 经射手座、经“香江-F → 射手座”提交的测试数据未被 cloud 收到。
这两组没有形成“cloud 收到请求并回复，但校园网收不到”的证据，不能据此判定学校过滤回程。
cloud 是最终应用接收端，不是射手座入口抓包点；未到 cloud 仍可能发生在代理握手、节点转发、
中间路径或 cloud 主机抓包点之前，尚不能指出具体丢包设备和方向。

## 实验设计

1. cloud 在既有 UDP/51820 路径识别本轮随机标记，只回复匹配标记的数据。
   使用原始套接字观察和回显，不替换 WireGuard 监听器、不添加 peer，不改路由或防火墙。
   限时 15 分钟，最多回复 100 个唯一来源端口与请求编号组合，载荷不超过 1400 字节。
2. 每个请求携带独立编号；cloud 记录收到的源地址、端口、长度、编号，以及回复提交结果。
   客户端检查回复来源与完整内容，不能仅凭收到任意字节判成功。
3. 先用本机移动出口直达 cloud 做阳性对照，两种长度均成功，往返 22–26 ms。
4. 通过网络管理面板暂停 D321 借网，核实校园网 0 会话及物理有线网卡地址，逐条测试四种路径。
   每种代理路径使用独立临时内核，最终规则固定指定节点，不自动切换其他节点。
5. 测后再次核实 D321 为校园网 0，注销测试会话，恢复原借网。

## D321 校园网 0 的结果

下表每行均测试 80、1280 字节两种载荷，各一次；是有限样本，不代表长期稳定性。

| 路径 | cloud 收到测试数据 | cloud 提交等长回复 | D321 收到完整回复 | 往返时间 |
| --- | --- | --- | --- | --- |
| D321 → cloud | 两种均收到 | 两种均提交 | 两种均成功 | 均约 9 ms |
| D321 → 香江-F → cloud | 两种均收到 | 两种均提交 | 两种均成功 | 530 / 535 ms |
| D321 → 射手座 → cloud | 两种均未收到 | 无对应请求 | 两种均超时 | — |
| D321 → 香江-F → 射手座 → cloud | 两种均未收到 | 无对应请求 | 两种均超时 | — |

直接射手座的临时内核记录连接超时。客户端的 `submitted` 只表示数据交给本地套接字，
不等于射手座已经收到，更不等于已经从射手座发往 cloud。

## 移动补充对照与实验边界

- 本机移动经射手座的 80 字节请求完成完整回显；cloud 确实能接收到该代理出口的数据。
- 移动经射手座的部分 1280 字节请求到达 cloud，cloud 提交等长回复；客户端却收到
  1230 字节 SOCKS 数据，其中 10 字节为封装头、1220 字节为有效内容，未通过完整性校验。
  另有请求超时。这是本轮观察到的额外 UDP 转发/大小问题，尚未定位到具体组件，不能归因于校园网 0。
- 移动经“香江-F → 射手座”的最终补测，80 字节请求超时；1280 字节请求到达 cloud，
  客户端也只取到 1220 字节有效内容。该组合本轮没有通过完整 UDP 回显验证。
- 两次临时代理入口曾因 Windows 拒绝 UDP 端口绑定而未启动；这类连接拒绝已排除，
  最终补测先验证 TCP、UDP 均能绑定，并检查内核启动日志。
- D321 与本机不是同一设备、同一接入区域，订阅显示名相同也不能证明实际端点一致。
  后续解析出现不同节点 IPv4；本轮跨机对照不能独立证明运营商是唯一变量。
- cloud 与 D321 时钟约有 16 秒偏差，以请求编号关联，不直接相减跨机时间。表中 RTT 在发送端测量。

## 对之前推测的修正

之前本机无线校园网 0 的原生 WG 握手失败，与本次 D321 有线校园网 0 的普通 UDP/51820
回显成功并不矛盾：设备、出口、协议内容不同。不能由这两组试验直接推出 WireGuard 指纹被过滤。

之前“香江-F → 射手座”访问 GitHub、百度成功，验证的是经代理的网页 TCP 请求。
本轮验证的是应用 UDP 数据转发，两者不能相互替代；原网页方案仍应按实际用途验证。

目前能确认的双向路径为：

```text
D321（校园网 0） → cloud → D321
D321（校园网 0） → 香江-F → cloud → 香江-F → D321
```

若使用“香港 → 射手座”，正常回复应沿已建立的代理链反向返回，无需另设计一条绕行回程。
但该链路的完整 UDP 转发本轮未通过，不能标记为已修复。
普通 UDP 回显成功也不等于 WireGuard 的握手、加密数据和转发已可用；本轮未部署云 WG 新方案。

## 证据与恢复

- cloud 日志最终记录 12 个唯一请求及 12 次回复提交，并记录接收器已停止。
- 独立 tcpdump 捕获 8 个包：D321 经香港两种长度，以及本机移动直接经射手座两种长度，
  每个请求各有对应出站回复。抓包窗口没有覆盖所有实验；快照只保留前 160 字节，
  不能用它证明长包全部内容相等。完整回显依据客户端逐字节校验。
- D321 原借网服务已复核为 Running / Auto，本机仍为中国移动；临时代理进程及含身份信息的配置已清理。
- 原始 JSONL、PCAP、接收器和客户端代码保存于本机诊断目录，不将节点身份或账号信息提交公共仓库。

下一步需要射手座入口/出口的同步记录，或校园网关与云安全组日志，才能继续区分握手、转发、正向和回程故障。
本轮已排除“校园网 0 所有 UDP 回包都被拒绝”这一解释，没有取得学校具体过滤规则。
